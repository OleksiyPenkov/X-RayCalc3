Overview

XRC_MCP is a console program that exposes the X-Ray Calc 3 calculation engine to AI assistants over the Model Context Protocol (MCP). An MCP client such as Claude Code starts XRC_MCP.exe, talks to it as JSON-RPC 2.0 over standard input and output, and calls its tools: calculate a reflectivity curve, score a mirror design, run the universal optimizer, fit a measured curve, and read or write .xrcx project files.

The engines are the GUI's own. The curve, the χ² and the figure of merit the server returns are the numbers X-Ray Calc 3 and XRFCalc display for the same structure, and a fit written by the server opens in the GUI as an ordinary project file. This lets you have an assistant prepare, run and compare fits while you verify every result in the GUI.

Property Value
ExecutableXRC_MCP.exe, 64-bit only, in the same folder as the GUI
TransportJSON-RPC 2.0 over stdio; one JSON object per line, UTF-8
Tools18, grouped below
Long jobsoptimize_mirror and fit_xrr run in the background and are polled
RecordEvery call and result appended to log\calls.jsonl

Installation and Registration

The server needs no configuration file. It takes one mandatory argument, the working directory that becomes its sandbox (see below):

XRC_MCP.exe --workdir "D:\Experiments\RuC-2026-09"

Register it with Claude Code once per experiment directory. The name xrc is how the assistant refers to the server:

claude mcp add -s user xrc -- "C:\Program Files\X-RayCalc3\XRC_MCP.exe" --workdir "D:\Experiments\RuC-2026-09"

Other MCP clients register a stdio server the same way: the command is the path to XRC_MCP.exe, the arguments are --workdir and an absolute path. Nothing in the server depends on the current directory of the process.

To verify the registration, ask the assistant to call describe_server. The reply states the server version, the git revision it was built from, the Henke table directory in use, the unit conventions, and a one-line summary of every tool.

OmniThreadLibrary 3.08: If you build the server yourself, it needs OmniThreadLibrary 3.08 or later. With an older library a job stays at iteration 0 for ever and the server will not exit. See Source Code > Dependencies.

The Working Directory

Every path the server reads or writes lies under the working directory. It is created on first start with four subfolders:

<workdir>\
  projects\        .xrcx files the server writes (save_project) and reads (load_project)
  jobs\            one folder per job: request, progress log, curves, results
  inbox\           measured curves that YOU put there; the server never writes here
    <specimen>\    one folder per specimen, any number of data files inside
  log\
    calls.jsonl    every tools/call and its result, appended, never truncated

A path argument that resolves outside the working directory (a rooted path, a drive letter, a UNC path, or a .. segment) is refused with the error path_outside_workdir; it is never silently remapped.

The journal is the record. log\calls.jsonl holds one line per call with a timestamp, the tool name, the full arguments and the full result or error. Long numeric arrays such as curves are replaced by their length and the SHA-256 of the file they were written to. Keep it with the experiment.

Units and the Structure JSON

The conventions are the program's: thickness, roughness σ and wavelength in ångström, density in g/cm³, angles as the grazing angle θ in degrees (not 2θ). Wherever a wavelength is expected, a photon energy in eV is accepted instead and converted with λ[Å] = 12398.42 / E[eV]; the wavelength actually used is echoed back. (The engine itself looks the Henke tables up with 12398.6; describe_server reports both constants.)

Every tool that takes or returns a layered structure uses one JSON form, listed from the substrate to the surface:

{
  "substrate": {"material": "SiO2", "density": 2.2, "sigma": 3.0},
  "buffer":    {"material": "Ru", "thickness": 197.0, "sigma": 3.0},
  "stacks": [
    {"N": 30, "layers": [
      {"material": "Ru", "thickness": 14.7, "sigma": 3.0, "density": 12.4},
      {"material": "C",  "thickness": 53.8, "sigma": 3.0, "density": 2.2}
    ]}
  ],
  "cap":       {"material": "Ru", "thickness": 20.0, "sigma": 3.0}
}
  • material is a Henke table name, matched case-insensitively (list_materials gives the valid names).
  • density is optional and defaults to the bulk value from the table; the value used is echoed. thickness is required; sigma defaults to 0 and N to 1.
  • buffer (between substrate and first stack) and cap (on top) are optional. Several stacks are allowed.
  • Numbers in the JSON replies are rounded to 6 significant digits; the curve files keep full precision (θ to 7 digits, R as %.8e).

Reference Tools

Tool Description
describe_serverCall it first. Reports the server version and git revision, the Henke directory, the unit conventions, the material-name syntax, the structure form, the limits, the working-directory layout, and a summary of every tool.
list_materialsThe Henke tables the server can use, optionally filtered by an element pool. Each entry gives the table name, formula, bulk density and atomic mass.
optical_constantsδ and β of n = 1 − δ + iβ for one material at one wavelength or energy, plus n, k and the nearby absorption edges. Unknown materials are refused with unknown_material.
list_templatesThe multilayer design templates (one period each: sub-layers with thickness rule, σ, density, capping variants) that optimize_mirror can start from, optionally filtered by a material pool.

Calculation Tools

Tool Description
calc_reflectivitySpecular reflectivity of a structure over a θ range at one wavelength: theta_min (default 0.05°), theta_max (default 5°, at most 90°), points (default 2000, at most 100 000), polarization (below) and an optional beam divergence delta_theta (default 0; when set, the FWHM in degrees of the Gaussian the curve is convolved with — a width the ±0.1° kernel cannot represent on the grid is refused with invalid_argument). The calculated R is clamped from below to r_min (default 10−7). Returns the curve inline when short enough and always as jobs\<id>\curve.dat; period_A, n_periods and structure_used (densities filled in); the Bragg peaks as {order, theta_deg, r_peak, fwhm_deg}; and critical_angle_deg. theta_deg is the calculated maximum, refraction shift included, not the kinematic θB: each order of the period of the first repeating stack (counted from the surface) is looked for between θB − 0.06° and the refraction-corrected angle + 0.06°, must lie more than 0.05° above θc and stand more than three times above the window minimum, and is left out otherwise. FWHM is taken between the interpolated half-maximum crossings, 0 when the curve does not fall to half on both sides. critical_angle_deg is estimated as √(2⟨δ⟩) from the thickness-weighted δ of the top 500 Å (substrate included where the film is thinner), not read off the curve. This is the GUI's curve for the same structure (see Calculation).
polarizationIn every tool that takes it: "sp" (default, the unpolarized average (Rs + Rp)/2) or "s". The engine has no pure-p path, so "p" is computed as "sp" and echoed as such.
evaluate_linesScores a structure against a set of X-ray emission lines (name, lambda or energy, weight) with the universal optimizer's own figure of merit; optional fitness overrides. A line may also be a bare symbol or a range such as "B-Si"; at most 16 lines, and exactly one stack must repeat. Refused with server_busy while optimize_mirror runs. The number is directly comparable with what optimize_mirror reports (see Universal Mirror > Figure of Merit).

Optimisation and Jobs

Two tools take longer than a request should wait for. They return a job_id at once and run in a background thread; the client waits with job_wait or polls job_status. One job runs at a time, and up to 16 more can queue behind it.

Tool Description
optimize_mirrorSearches for the periodic multilayer that best serves a set of emission lines with the XRFCalc particle swarm. Takes the optimizer configuration (lines, element_pool, excluded pairs, structure ranges, fitness, optimizer settings, substrate, template), a seed and top_k (default 5). The result holds the top_k distinct structures with genome, figure of merit, per-line results and the .xrfx package written for each.
job_statusState of a job without waiting: queued, running, finished, failed, cancelled or unknown, with the current iteration and budget, the best value so far, elapsed seconds and the last message.
job_waitWaits for a job and returns the job_status object plus waited_s. It returns as soon as the job is finished, failed or cancelled, or after wait_s seconds (default 300, at most 900). While it waits the server answers nothing else, so cancel_job cannot reach it; keep wait_s below the client's tool timeout.
job_resultThe result of a finished job. Fails with job_not_finished while it runs, job_failed when it ended in an error, job_cancelled when it was stopped.
cancel_jobAsks a job to stop and returns its state. A running job usually stops within a second or two; poll job_status to see it become cancelled.
Determinism and lifetime: With the same seed and inputs, optimize_mirror and fit_xrr give identical results on the same device; the seed used is echoed. With device: "auto" a machine with a GPU and one without can differ in the last digits, so pin "cpu" or "gpu" for bit-for-bit repeats. Jobs do not survive the server: if the process ends, running jobs are lost and job_status reports unknown after a restart. Each job's folder jobs\<job_id>\ keeps its request, progress log and outputs.

Fitting

Tool Description
fit_xrrFits a layer model to a measured curve with the GUI's LFPSO, minimising the same χ² X-Ray Calc 3 displays (see Fitting). Returns a job_id; the result is read with job_result.

The main arguments:

Argument Meaning
measurement_id or curveThe measured data: an inbox id such as "RuC-07/xrr.dat", or the curve inline. Every measured intensity must be positive, since the χ² takes its logarithm.
structureThe start model in the structure JSON.
freeWhich values may vary. Each entry addresses one layer by its stack index (from the substrate up, or "cap" / "buffer") and layer index, and lists the parameters that take part: "thickness", "sigma", "density". By default a repeating stack keeps the start model's period, so freeing its thicknesses fits only their ratio. Add {"target":"period","stack":k} to fit the period d of repeating stack k as well; at least one thickness of that stack must also be free, and it cannot be combined with profile. The substrate, scale, background and resolution are not free parameters; asking for them is answered with not_fittable (the scale is solved inside the objective instead, see scale_solve below). period_mode in the result says how each stack was treated.
boundsOne min / max pair per free parameter (stack, layer, parameter), or per free period (target: "period"). Omitted bounds default to the start value ±30 % (a period too); the start value must lie inside the range. A parameter that starts at 0 (for example an omitted sigma) has no default range and needs explicit bounds; an omitted density is first replaced by the bulk value. Sigma and density bounds are clamped at 0; thickness and period bounds must be above 0. Every fitted value stays inside its bounds, and the result's bounds_used lists the ranges that applied.
lambda or energy, theta_rangeThe wavelength (or photon energy) of the measurement: required with an inline curve; with measurement_id it defaults to the .xrdml file's own wavelength (the weighted Kα doublet, 1.541874 Å for Cu) or else meta.json's lambda, and an explicit value overrides both. theta_range is an object {"min", "max"} in degrees θ (never 2θ); default the whole curve.
scale, scale_autoThe anchored multiplier applied to the measured intensities before the fit (the manual's Normalize step), default 1, stored with the curve in measured.dat and fit.xrcx. "scale_auto": true (or "scale": "auto") is the GUI's Normalize (Auto): the largest measured intensity below auto_theta_max (default 0.5°) is set equal to the start model's reflectivity at that angle.
scale_solve, scale_solve_windowDefault true: the measured scale is treated as a nuisance parameter and solved in closed form for every candidate structure, held between 1/(1 + scale_solve_window) and (1 + scale_solve_window) times the anchored scale (default 0.2, a fraction: a factor of 1.2 either way), so the χ² is the best any scale in that window can give. The result reports chi2_scale ("solved" or "anchored"), scale_ratio (the solved factor over the anchor), scale_solved, scale_clamped and chi2_scale_definition; the files and the .xrcx keep the anchored scale, and residual.dat says in its header which scale it is at. "scale_solve_window": 0 pins the solved scale to the anchor. With "scale_solve": false the χ² is the anchored one of every earlier version. The GUI's Solve scale in χ² and Window are the same option with the same defaults; the physics is in Solving the Measured Scale.
smooth{"passes": n}, 0 to 10, runs the GUI's Data > Smooth on the measured curve before the fit: each pass is a moving average of window 5 on the linear intensities, which leaves the first points as they are and flattens the last few, so trim the ends with theta_range. Order: scale, then smooth, then the theta_range trim, as in Data Conditioning.
optimizerpopulation (default 500), iterations (default 100), tolerance (default 0.005: the run stops early once χ² falls below it), shake, range_seed and use_constriction (all default true), and device: "auto" (default, the GPU when describe_server names one in server.gpu), "cpu" or "gpu" (refused without a usable GPU). The result carries optimizer_used with every default filled in, and device_used. The reported χ² is always recomputed on the CPU (chi2_recalc, with consistency_warning when the two disagree); gpu_error says why a run asked to use a GPU fell back to the CPU. See GPU Acceleration.
profile, paired, seedprofile fits a polynomial (order optimizer.poly_order, default 1) of each free parameter — thickness, sigma and density alike — over the periods of the one repeating stack (the GUI's polynomial mode; exactly one stack must have N > 1). paired (for example ["sigma","density"]) keeps chosen parameters at one value per layer. The per-period arrays start at the period nearest the surface. seed is the random seed.
polarization, resolution, chi2, r_minpolarization as in calc_reflectivity (default "sp"). resolution: FWHM in degrees θ of the Gaussian the calculated curve is convolved with (default 0.015, held fixed); the kernel stops at ±0.1° and is normalised, χ² leaves out the points within about 0.1° of each end of the fitted range, and a grid too coarse or too short for the kernel is refused. chi2: theta_weight 0–5 (default 0), point_weight (default true: a point more than 3× its moving average is weighted by that ratio) and movavg_window (default 0.05 of the points); the sum is 1000/(n−1) Σ[(log I − log R)/log R]²·w (see the cost function). r_min (default 10−7): the floor the calculated reflectivity is clamped to; no measured point is dropped. It is also the chart minimum stored in the .xrcx.

The result holds the fitted structure (with the expanded per-period profile when profile was set), χ² beside chi2_start and chi2_plain (the same sum without point and θ weights, at the scale solved for chi2; reported, never minimised; chi2_start is scored at the start model's own solved scale, scale_start_ratio), the scale mode and values, period_mode, out_of_bounds, iterations_run, elapsed_s, background (always 0), the start model, a report (the Bragg orders measured against calculated, the plateau edge, the Kiessig fringe contrast, the residual by band, values within 5 % of the range from a bound; also written as report.json with the scale mode beside every χ² it holds; the report compares the model with the anchored measured curve, so with scale_solve its ratios and bands differ from residual.dat by log10(scale_ratio)), the measured, calculated and residual curves as files under the job folder, and the path of the fit.xrcx written for the fit. Open that file in the GUI to check the fit yourself.

Inbox: Measured Curves

Measured curves reach the server through the inbox\ folder, one subfolder per specimen. You copy the files there; the server only reads them and never modifies them.

Tool Description
list_measurementsEvery file in the inbox, optionally filtered by specimen, with its id "<specimen>/<file>", size, SHA-256, modified time, and the specimen's metadata file if present.
get_measurementOne curve as [θ, intensity] pairs, parsed the way the GUI parses a data file (see File Formats): two columns separated by tab or space, comma accepted as the decimal mark, non-numeric lines reported as the header. An .xrdml file is read raw, as Data > Load reads it: its 2θ axis is brought to θ, its counts to counts per second normalised to 1 at the maximum, and the wavelength the file implies overrides meta.json (lambda_source says which). A non-positive intensity is replaced by the smallest positive one before it, and "theta_unit": "2theta" in meta.json halves the angles of a two-column file. max_points (default 2000) decimates a long curve for inline return; the file stays raw.

assess_xrr: is this curve worth fitting?

assess_xrr runs the eight measurement checks of the GUI's Data > Assess XRR quality on an inbox file, before anyone fits it. It reads the .xrdml itself, because the decisive checks are count rates and the counting time exists only there; a two-column file still works, and every check that needs a fact the file does not carry answers "unknown". Nothing is written anywhere.

Argument Meaning
measurement_idThe inbox file, as list_measurements reports it.
structureThe design, optional: the same structure object calc_reflectivity takes. Unlike the other tools this one accepts a bare substrate, "stacks": [], for a glass reference. With a design the checks that need a period, a total thickness or a critical angle can answer, and the design's reflectivity on the measured range, convolved with resolution (default fit_xrr's 0.015°), says what the measurement could have shown.
lambda or energyFor the design; defaults to the file's wavelength or meta.json's.
detector_max_cpsThe detector's linear count-rate limit, judged against the rate the detector itself saw (attenuation factors out). Without it the counting check reports the peak rate under "unknown"; no limit is built in.
sample_length_mm, beam_width_mmPlace the footprint knee asin(beam / length).
order_visible_factor, min_points_per_fringeAn order counts as visible this many times above the background (default 3); the sampling check warns below this many points per Kiessig fringe (default 3) and fails below 2 whatever is given.

The result carries checks — counting, plateau_vs_first_order, total_reflection, orders_visible, range_below_background, sampling, footprint, zeros, each {value, threshold, verdict, why} with the numbers behind it — the background, the design's period, thickness and critical angle, the overall verdict (the worst check) and summary_text, one line per check for the client to file with the specimen. Every angle is theta_deg with the file's two_theta_deg beside it. No count-rate or fraction limit is built in. The fixed rules are: a first order above the plateau fails; a scan that starts at its own maximum, or at or above the design's critical angle, fails; fewer than two points per fringe fails. The warnings compare the measurement with the design scaled to the measured plateau (a plateau-to-first-order ratio above the design's; fewer visible orders than it predicts), with the footprint knee (the low-angle maximum below it), or flag any zero or negative count. range_below_background only reports the fraction and is always "unknown". The background is the median of the last 100 points; the fringe spacing is λ/(2 × total thickness) and the order spacing λ/(2d), converted to degrees; the design is always computed unpolarized (sp).

Projects

Tool Description
save_projectWrites projects\<name>.xrcx that opens in the GUI with no conversion: the structure as the active model, the calculated curve beside it (without a job: λ = 1.54043 Å unless given, θ 0.05–5°, 2000 points, s polarization as the GUI's params.dsc has it — so it can differ from a default calc_reflectivity curve, which is sp), and optionally a measured curve (an inbox id or a job's curves via curves.job_id). A project saved from a fit job carries the job's own fit settings, so it opens as the fit that ran. Refuses to overwrite unless overwrite: true.
load_projectReads a project back: the active model's structure in the structure JSON, its profile extensions, the calculation parameters (angles always as θ), and a summary of the embedded curves.
list_projectsThe .xrcx files in projects\ with size, SHA-256 and modified time. Nothing is written.

Example Session

A typical exchange, with the assistant's tool calls in order. The curve RuC-07\xrr.dat was copied into the inbox beforehand.

  1. describe_server — confirm the revision and the Henke directory.
  2. list_measurements → finds "RuC-07/xrr.dat"; get_measurement with max_points: 200 to look at the curve.
  3. assess_xrr with the nominal structure — is the curve worth fitting: the plateau against the first order, the orders visible, the points per fringe, the zero counts.
  4. calc_reflectivity with the nominal Ru/C structure (30 periods, d = 68.5 Å) at λ = 1.5406 Å — compare the Bragg peak position with the measurement.
  5. fit_xrr with the period of stack 0 and both layer thicknesses free, smooth: {"passes": 1}, theta_range: {"min": 0.3, "max": 4.0}, seed: 1 → job_id: "fit-20260922-143012-a1b2".
  6. job_wait until finished (tens of seconds on the CPU, much less on a GPU; the result's elapsed_s and iterations_run give the real cost).
  7. job_result → fitted_structure (d is report.period_A; Γ follows from the layer thicknesses), chi2, and the path of fit.xrcx.
  8. save_project with name: "RuC-07-fit" and curves.job_id: "fit-20260922-143012-a1b2" → projects\RuC-07-fit.xrcx, which you open in X-Ray Calc 3 to inspect and refit.
Practice: The lab's rule of thumb for the LFPSO is 100 iterations with 500 to 1000 particles: population wins over iterations. The server's defaults are 500 particles and 100 iterations, the lower end of that rule. They are not the GUI's defaults (the GUI's own population is 1000); the result's optimizer_used lists every value the run used.

Security

  • Sandbox: the server can only read and write under its working directory. A path outside it is refused, never remapped.
  • Read-only inbox: no tool has a write path into inbox\; your measured data cannot be altered by an assistant.
  • No network: the server speaks only over its own stdin and stdout to the client that started it. It opens no ports.
  • Journal: every call and result is appended to log\calls.jsonl; the file is never truncated by the server.
  • Structured errors: failures are returned as {code, message, detail}. The process never shows a dialog or waits for a key, so it is safe to run unattended.

Smoke Test

The repository ships an end-to-end check, XRC_MCP\smoke\session.ps1. It starts the server in a throwaway working directory, calls every one of the 18 tools over one live stdio session (jobs are submitted, polled, waited for with job_wait and read; one is cancelled), and checks the Ru/C Bragg-peak angle, seed determinism of the optimizer and the fit, the path_outside_workdir refusal, that the inbox is byte-identical afterwards, and that the journal holds exactly one line per call.

pwsh -File XRC_MCP\smoke\session.ps1

Exit code 0 means every check passed; -KeepWorkdir leaves the work directories behind for inspection. It takes a few seconds.
