# GPU evaluation of the LFPSO population (3.9.0)

_2026-09-21. Worktree `.claude/worktrees/gpu-lfpso`, branch `worktree-gpu-lfpso`._

## Why

The prototype (scratchpad `gpubench/gpuproto.dpr`, `parratt.hlsl`) measured on a Ryzen 9 9950X3D + RTX 5080:
one LFPSO iteration 105-266x faster at population 5000 (150-period W/B4C, 2000 points: 12.0 s -> 70 ms),
with GPU accuracy against a double-precision reference at CPU level (mean |log10 R| error 1.0e-3 vs 1.5e-3).
The Parratt recursion is 97-100% of a particle's cost on the CPU.

## Design

- **`Shared/Math/unit_gpu_calc.pas`** - `TGpuEvaluator` (D3D11 compute, Win32 and Win64, no extra runtime:
  `d3d11.dll`, `dxgi.dll`, `d3dcompiler_47.dll` ship with Windows 10+).
  - Picks the hardware adapter with the most dedicated memory; compiles the embedded HLSL once per process.
  - Kernel `Reflect`: one thread per (particle, angle); Parratt from the substrate up with nothing stored
    per layer. Cancellation-free form `(eps.re - 1) + sin^2(theta)` (the naive `eps - sin^2 t` near t = 90
    deg costs 2x accuracy). All TRoughnessFunction values, S and S+P.
  - Kernel `ChiSquare`: one group per particle; Gauss convolution (TCalc's own weights) + weighted chi2
    reduction. Per-point weights (MovAvg peak ratio x theta weight) are precomputed on the CPU.
  - Dispatches are chunked by particles (TDR safety, 65535 group limit).
- **`unit_calc.pas`** - `TCalc` exposes what the GPU needs and takes back a raw curve:
  `GpuInputs` (theta, log data, per-point chi weights, convolution weights, chi range, normaliser) and
  `FinishRawCurve` (raw R -> convolved Results, as Run would leave them). Convolution weights move into one
  function both paths use.
- **`TLFPSO_BASE`** - `UseGPU` (default False in the engine; callers opt in), `DeviceUsed`, `GpuError`.
  `Run` creates the evaluator when asked and the mode is cmTheta; any failure falls back to the CPU path.
  `FindTheBest` GPU path: models built in parallel on the existing workers (Reset, FillModel, Generate, pack),
  one GPU evaluation, reduction; the best particle's curve is read back and finished on the CPU only when it
  improves the global best.
- **GUI** - `TCalcOptions.UseGPU` (default True), a checkbox on the Calc & Fit settings page.
- **XRC_MCP** - `fit_xrr` `optimizer.device`: `"auto"` (default) | `"cpu"` | `"gpu"`; `"gpu"` without a usable
  GPU is refused. The result echoes `device` in `optimizer_used` and reports `device_used`.
- **Version** 3.9.0.930 (dproj four groups + `VerInfo_Keys`, installer `.iss`).

## Tests (DUnitX; GPU tests pass with a note where no GPU exists)

1. CPU-only: chi2 rebuilt from `GpuInputs` + `FinishRawCurve` equals `CalcChiSquare` (weights, tail, theta
   weights 0-5, MovAvg).
2. GPU raw curve vs a double-precision Parratt reference: every roughness function, S and S+P.
3. GPU chi2 vs CPU chi2 for perturbed models, all theta weights, MovAvg on/off, with and without resolution.
4. `TLFPSO_Periodic` with `UseGPU`: improves on the start, `DeviceUsed` names the GPU, best curve present;
   cmLambda falls back to the CPU.
5. MCP: `device` parsing/refusal and echo.

## Outcome (2026-09-21)

Integrated engine, same seed and request, one LFPSO iteration, 32 CPU threads vs RTX 5080 (Win32, runs of
5-20 iterations, so the ~70 ms device creation per fit is included):

| model | pop | CPU | GPU | x |
|---|---|---|---|---|
| Si/Mo 10 periods, 200 pts | 500 | 25.6 ms | 13.5 ms | 2 |
| W/Si 40 periods, 1000 pts | 500 | 178 ms | 9.8 ms | 18 |
| W/B4C 150 periods, 2000 pts | 500 | 1.18 s | 16.2 ms | 73 |
| same, S+P | 500 | 1.84 s | 16.0 ms | 115 |
| W/B4C 150 periods, 2000 pts | 5000 | 11.5 s | 66.7 ms | 173 |

Found on the way:
- `unit_calc`'s `Log10` is `FastLn(x) / (2 ln 10)`, not log10. `CalcChiSquare` only takes ratios of two logs
  so the scale cancels; `GpuInputs.LogData` must be a true log10 because the shader's is.
- The parallel model build did not scale (69 ms for 5000 particles on 32 threads, worse than 4 threads):
  every particle reassigned the shared material strings (interlocked refcount writes from all threads to one
  cache line) and allocated a fresh `TLayersData`. Fixed with a per-model `FillScratch`, pointer-compare
  string assignment (`SetName`, `SetMaterial`) and a per-layer material memo in `PrepareLayers`: 7 ms. The
  CPU path benefits too; its results are unchanged (the revision-pinned MCP test still matches).
- The GPU chi2 floor on a self-generated curve (~0.003) differs from the CPU's (0): the reported chi2 and
  curve are rescored on the CPU at the end of the run (`RescoreBestOnCpu`).

Review fixes (independent code review, same day):
- OmniThreadLibrary 3.08's `Parallel.For` never hands a loop-body exception back; the caller waits for ever.
  Both evaluation loops now catch inside the body (`KeepFirstError`) and raise after the loop (`RaiseKept`):
  the GPU path falls back to the CPU, the CPU path fails the fit instead of hanging. The CPU loop had this
  hang before 3.9.0.
- A GPU failure while reading back the best curve falls back to the CPU (`CpuCurveOf`).
- Tolerance stop: near the GPU's chi2 floor the incumbent is checked on the CPU (`ToleranceMetOnCpu`).
- Shader: no phase term at the substrate step (sincos of ~1e8 is vendor-defined); shaders cached both or
  neither; a failed GPU probe is retried after a minute; non-positive intensities are named.
- Tests: injected GPU failure mid-run (`TGpuEvaluator.FailAfter`), a particle build that raises with and
  without the GPU (guarded by a timeout so a hang fails instead of stopping the suite).

## Verify

Suite green, `XRC_MCP/smoke/session.ps1` PASS, Win32 + Win64 builds of XRayCalc3 and XRC_MCP.
